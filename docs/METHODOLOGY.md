# What this experiment measures

This is a launch-week task experiment, not a model leaderboard or a quota calculator. Two historical JavaScript bugs are attempted once each with **Sol medium**, **Astra low**, **Astra medium**, and **Astra high**. The eight conditions were selected before running the pilot. They are run sequentially in that order within each case, with no retries to replace bad outcomes.

## Why these questions

On September 5, 2026, users were asking [which Astra reasoning effort works for them](https://x.com/nummanali/status/2096012041727144205), [whether Astra is worthwhile when Sol already works](https://www.reddit.com/r/codex/comments/1w7qwt3/sol_v_astra/), and [which effort combination fits ongoing development](https://www.reddit.com/r/codex/comments/1w7rjth/astra/). Replies disagreed and described different tasks, plans, and tools.

This motivates publishing comparable tasks and inspectable outcomes. It does **not** establish demand for a new CLI, nor prove that these two tasks resemble those users' projects. The command is a small way to reproduce the evidence. [Astra Room Test](https://github.com/SushaanthSrinivasan/astra-room-test) already compares efforts on a Blender task; this experiment adds a Sol baseline and independently executed regression checks for coding tasks.

## Tasks and grading

| Case | Public report | Starting commit | Known upstream fix | Checks |
|---|---|---|---|---|
| `abort-delay` | [p-retry #97](https://github.com/sindresorhus/p-retry/issues/97) | `6ac326b188834f4af5a54cedc114f67f0f510613` | `2aba573c0fdca165c4d95262f51ae56902f2f892` | 7 |
| `abort-cleanup` | [p-retry #71](https://github.com/sindresorhus/p-retry/issues/71) | `285fdc3f890a6f3d199b3d4abb0bad7c172c2233` | `95a3a4a667494ac585e6ba7ff5154f04d30941f2` | 8 |

The task statements are paraphrases of real reports, with explicit boundary cases. The only adaptation to the upstream implementation is an import pointing at a vendored MIT dependency. The exact prompts are generated by [`promptFor`](../src/cases.mjs). Each fresh Git workspace gets the same starting code and three visible smoke tests. The model may run its own temporary tests; only its final `index.js` is copied into a pristine fixture for grading. Changes to a model's local tests, dependencies, or metadata do not change the grade.

The external grader tests cancellation in four lifecycle locations, ordinary retry/backoff behavior, error identity, listener cleanup on seven completion paths, and preservation of another caller's listener. Backoff observation is deterministic: its requested duration is recorded and the timer is fast-forwarded. A pre-aborted retry must not schedule a backoff. The checks are public but are not placed in the model workspace or included in its prompt. They are not a security boundary against a malicious agent.

Before any model trial, the original source was verified to fail the relevant checks and the upstream fix to pass every check. `npm test` repeats that verification. This is a focused regression suite, **not the full upstream test suite**, and a passing score does not prove a production-ready fix.

A subsequent [upstream runtime check](https://github.com/sjh9714/astra-sweetspot/tree/main/research/upstream-2026-09-05) applied unchanged historical AVA tests to the same eight candidate files and to both controls. It found no additional failures relative to the starting code in that environment: 63/63 on `abort-delay`, and 12/13 on `abort-cleanup`, including a historical error-message assertion that also fails on the original and known fix. This post-pilot check has separate logs and does not replace the original grades. Upstream lint and type tests were not run.

## Harness and measurements

- Codex CLI 0.153.0, existing ChatGPT authentication, Node 22 on macOS for the published pilot. Exact versions, platform, and architecture are in every receipt.
- `codex exec --ignore-user-config --ephemeral --sandbox workspace-write --json`; explicit requested model and effort, `approval_policy="never"`, and a 180-second process deadline. The runner disables web search, project instruction loading, apps, hooks, memories, goals, and multi-agent tools for that invocation. It does not edit the user's configuration or ignore execpolicy rules.
- Codex still has its own system instructions and locally discovered capabilities. This is not a hermetic harness. The same invocation policy is applied to all conditions. Neither the model nor the package needs network access to install fixture dependencies; model inference itself requires a connection.
- **Seconds:** wall time from spawning Codex until it exits, including startup, reasoning, edits, and any tests the model chooses to run. External grading is excluded. Network latency, server load, and fixed run order can affect the result.
- **Tokens:** the CLI's `turn.completed.usage` fields. Input includes cached input; do not add them together. `reasoning_output_tokens` is a subset of `output_tokens`, not an extra output total. `cache_write_input_tokens` is preserved when reported. Repeated context across tool calls may be counted repeatedly. From v0.1.2, each counter is summed only when every completed turn supplies a valid nonnegative integer and the total stays within JavaScript's safe integer range; otherwise its run total is `null`, never a partial sum. These are **not** subscription quota, unique prompt size, or actual money paid.
- **Requested vs observed model:** the requested identifier is recorded. `observedModel: null` means the JSONL stream did not expose the served model; no independent model identity verification is claimed.
- **Checks:** passed / total external assertions. Model exit status is shown separately. A timed-out or failed run is retained even if a partial patch happens to pass the grader.
- Receipts include source, prompt, grader, candidate, and patch SHA-256 hashes. Sanitized receipts, candidate patches, and candidate files are published. Raw JSONL, stderr, and the last model message stay private by default; they can include local paths and tool output.

### Usage-field correction

On September 5, 2026, inspection of the original event logs found that the v0.1.0 collector had omitted two fields the CLI actually provided: `reasoning_output_tokens` and `cache_write_input_tokens`. Version 0.1.1 retains both. A reported zero stays zero; an unavailable field stays `null`.

Both fields were restored to all eight pilot receipts from their original `turn.completed` records. Each receipt directory now includes that original usage-only event as `usage-event.json`; `usageSupplement` records its hash, the recovery time, and the added fields. The events contain only a type and numeric usage counters. Full transcripts remain private. CI compares the event, receipt, and collector output.

No trial was rerun. The existing input, cached-input, output, time, status, patch, and grading values are unchanged. Reasoning counts are already included in output and must not be added to it; see [OpenAI's usage example](https://developers.openai.com/api/docs/guides/reasoning#managing-the-context-window) and the [Codex 0.153.0 token fields and display calculation](https://github.com/openai/codex/blob/rust-v0.153.0/codex-rs/protocol/src/protocol.rs#L2393). All eight events reported zero cache-write tokens; this does not establish a general cache-write or subscription-billing policy. The compact table retains its original columns; `report --json` includes the recovered fields and their evidence.

### Incomplete usage totals

On September 6, 2026, an offline replay found a second collector defect: v0.1.1 summed the available values even when another completed turn omitted the same field. For example, input counters of `100` and missing produced a run total of `100`, although the full total was unknown. The same error occurred when the missing event came first.

Version 0.1.2 keeps that counter `null` once any completed turn omits it or supplies an invalid value. Later valid events cannot restore a complete total. Explicit zero remains a reported value, fully reported counters still sum, and totals outside JavaScript's safe integer range also become `null`. This describes the completed events received by the collector; it cannot detect events missing from the stream entirely or supply usage for failed turns.

The [offline regressions](../test/runner.test.mjs) cover missing fields at the beginning, middle, and end of three completed turns for all five counters; invalid values; a missing usage block; zero; and integer overflow. They reproduced failures before the fix. All eight original usage-only events still match their published receipts under the corrected collector. No pilot data was changed and no model trial was rerun. This defect was reproduced in synthetic event sequences, not observed in one of the published runs or claimed as an OpenBench defect.

## Limits

One sample per condition cannot estimate reliability or variance. Both bugs are small, historical, public, and from the same package; they may have appeared in training data. They are not held-out evaluation tasks. This says little about large repositories, visual work, long contexts, research, MCP-heavy workflows, or the maximum capability of either model. The author's account was also used for ordinary work, so subscription percentage changes cannot be attributed to a trial.

Interpret a run as a receipt for that particular task. Do not extrapolate a universal best effort or a cost-saving percentage. A useful next contribution is a **different real task** with a known failing starting state, a reproducible check, and permission to publish its code—not more repetitions selected because they favor one model.

## Reproduce and contribute

```sh
npx astra-sweetspot
npx astra-sweetspot run abort-delay --model astra --effort medium
npx astra-sweetspot grade abort-delay /path/to/candidate/index.js
```

The first command reads bundled data and invokes no model. `run` consumes your Codex usage and saves everything in a new `~/.astra-sweetspot/runs/…` directory. It never modifies your current repository or uploads files. Node 20+, Git, an authenticated Codex CLI 0.153.0+, and access to the requested model are required. The CLI's [documented exec options](https://learn.chatgpt.com/docs/developer-commands#codex-exec) explain its authentication and configuration behavior.

Before sharing, inspect the patch and receipt. Submit both together, describe the task and environment, and keep unsuccessful attempts. Do not submit authentication files or raw private logs. Community submissions are labeled separately from the author's pilot.
